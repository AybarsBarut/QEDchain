# ChainGuard

A fixed-capacity Ada 2012 / SPARK 2014 hash-chain library and Windows CLI for a kernel-less anti-cheat experiment. Hash game parts, link their fingerprints, and let a server request selected segments. Local GNATprove results are the evidence for the library's safety and integrity contracts.

```text
game part files -> CLI streaming SHA-256 -> payload hashes
                                             |
                              Chain.Append / SHA-256
                                             |
                               CGUARD01 binary chain
                                             |
                        deterministic segment selection
                                             |
                         Verify_Link / Segment / Chain
```

## Local verification

Install [Alire for Windows](https://alire.ada.dev/docs/getting-started), then run from PowerShell 5.1 or 7:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\check.ps1
```

This builds both executables, runs the Ada and CLI integration tests, and runs GNATprove. Any failed test, unproved check, missing proof result, or skipped analysis fails the command. No make, bash, WSL, GitHub Actions, or cloud CI is required by these scripts. Alire may provision its own Windows dependencies on first use; allow the initial downloads to finish.

The manifest pins GNAT/GNATprove 16.1.0 and GPRbuild 26.0.1. Alire 2.1.1 was used for the recorded run. The scripts find `alr` on PATH or in the standard `C:\Program Files\Alire\bin` installation.

Individual commands:

```powershell
alr build
.\scripts\test.ps1
.\scripts\prove.ps1
```

## What is proved

**Silver:** absence of run-time errors throughout every package in `src`: initialization, array/range bounds, arithmetic checks, aliasing and contract call safety. SHA-256 uses modular 32-bit words and `Interfaces.Rotate_Right`. Its fixed buffer, padding, length encoding, schedule and compression are included in this analysis.

**Gold, for chain integrity:**

| Property | Encoding / evidence |
|---|---|
| Block hash validity | `Block_Valid` is the exact equality with `Compute_Block_Hash` |
| Consecutive link | `Link_Valid` requires a non-wrapping index increment, predecessor hash and valid current block |
| Whole-chain validity | Ghost `Chain_Valid`: valid genesis and every consecutive link |
| Append preserves validity | Pre/postconditions plus the proved `Index_Lemma`; length grows by one and the old prefix is unchanged |
| Full verification | `Verify_Chain'Result = Chain_Valid (C)` |
| Segment verification | Result equals ghost `Segment_Valid` for all legal windows |
| Conditional payload tampering | Proved `Payload_Tamper_Lemma` with an explicit distinct-computed-hashes premise |
| Sampling | Start is within bounds; exact deterministic state transition and selection formula |

SHA-256 functional correctness against the full FIPS mathematical specification is **tested, not formally proved**. Tests include the NIST empty, `abc`, 448-bit and million-`a` vectors, both streaming and one-shot. An independent .NET SHA-256 oracle checks actual serialized chain records, including file sizes around padding and 8 KiB streaming boundaries. The implementation follows [FIPS 180-4](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.180-4.pdf); this is not NIST certification.

No `pragma Assume`, intentionally unverified annotations, unchecked conversions, or suppressed proof checks are used. Gold here refers to the listed properties, not a proof of every possible security property.

## Cryptographic assumption and trust boundary

Changing a payload hash while preserving the block hash is detected **assuming no SHA-256 collision for those two encoded blocks**. Collision resistance is not proved. The ghost tamper lemma takes the concrete unequal-computed-hashes condition as a precondition and proves the consequence; it does not manufacture that condition through an axiom or `Assume`.

A hash chain alone does not authenticate its origin. A client can recompute a whole chain after changing files. A server therefore needs trusted reference hashes or authenticated checkpoints, an unpredictable challenge source, and a protocol binding replies to the session. This prototype verifies recorded metadata; it does not establish what code a game executed or re-read installed parts during `verify`. The deterministic xorshift64* sampler is a reproducibility tool, not a cryptographic challenge generator.

## Data model and API

`Block` stores an unsigned 64-bit index and three 32-byte hashes:

```text
Block_Hash = SHA256(BE64(Index) || Prev_Hash || Payload_Hash)
genesis: Index = 0, Prev_Hash = 32 zero bytes
```

`Chain (Capacity)` owns its block array; capacity defaults to 65,536 and can be set from 1 to 65,536. The library uses no dynamic allocation. Protocol positions are zero-based; Ada storage is `Blocks (1 .. Capacity)`. `Length` counts occupied entries. An empty chain is valid, giving `Append` its base case. Full verification returns false for a public record whose length exceeds its capacity.

`SHA256.Initialize`, `Update`, `Finish` and `Digest` expose streaming and one-shot hashing. A context accepts at most `2**61 - 1` bytes, matching the SHA-256 bit-length limit. `Finish` operates on a copy and can be repeated. Callers must satisfy the explicit `Update`, `Append`, sampling and segment-bound preconditions. `Pick_Segment` is a procedure with an `out Start` parameter because Ada 2012 functions cannot have an `in out` PRNG state parameter.

A nonempty segment validates its first block's own hash, every internal link, and the genesis rule when `Start = 0`. The first-block check was chosen to make tampering detectable whenever the selected window contains the modified block. Incoming and outgoing links outside the window are not checked. Empty windows are valid when their bounds are legal.

Sampling chooses among all starts `0 .. Chain_Length - Segment_Len` with replacement. A zero seed maps to a fixed nonzero state. Modular multiplication intentionally wraps modulo `2**64`; no checked arithmetic overflows occur. Modulo reduction is not claimed to be perfectly uniform.

Runtime builds keep range/overflow checks enabled. Expensive ghost pre/postconditions are proved statically and are not evaluated on every append, which would make bulk construction quadratic. Tests use explicit checks that always execute.

## CLI demo

Create a small manifest without a byte-order mark:

```powershell
New-Item -ItemType Directory -Force demo | Out-Null
0..11 | ForEach-Object {
    [IO.File]::WriteAllText((Join-Path (Resolve-Path demo) "part$_.bin"), "game part $_")
}
0..11 | ForEach-Object { "part$_.bin" } | Set-Content demo\manifest.txt -Encoding Ascii

.\bin\chainguard.exe build demo\manifest.txt -o demo\chain.bin
# built 12 blocks
.\bin\chainguard.exe verify demo\chain.bin
# valid (exit 0)
.\bin\chainguard.exe tamper demo\chain.bin --block 7 -o demo\bad.bin
# tampered
.\bin\chainguard.exe verify demo\bad.bin
# invalid (exit 1)
.\bin\chainguard.exe sample demo\chain.bin --count 5 --seed 42
```

The real session output is in [DEMO.md](docs/DEMO.md). Default sample length is `min(8, Length)`; `--length N` selects another length. Sampling an empty chain is a usage error. Exit codes are **0** valid/success, **1** invalid chain or sampled segment, and **2** usage, malformed-file or I/O error. All CLI exceptions are handled at the command boundary.

Manifests contain one unquoted file path per line. Relative paths resolve against the manifest's directory. Leading/trailing whitespace is trimmed; blank lines are errors. An empty manifest creates an empty chain. Spaces inside paths are supported. Use ASCII or UTF-8 without BOM for manifests.

## Binary format

All integer fields are big-endian; there is no native Ada stream representation in the file:

| Offset | Bytes | Field |
|---|---:|---|
| 0 | 8 | ASCII `CGUARD01` |
| 8 | 4 | Length, at most 65,536 |
| 12 + 104*i | 8 | Block index |
| 20 + 104*i | 32 | Previous block hash |
| 52 + 104*i | 32 | Payload hash |
| 84 + 104*i | 32 | Block hash |

The loader rejects bad magic, excess capacity, truncation, trailing bytes and incorrect file length before verification. The unproved CLI layer handles parsing and serialization; all integrity decisions call the SPARK library.

## Tests and source map

Tests build chains of 1, 2, 100 and 65,536 blocks; exercise all four field tamper cases at every position of a seven-block chain and every legal window; reject index wrap; and check deterministic and bounded sampling. CLI tests cover space-containing paths, independent hash/serialization results, malformed files, invalid numbers, empty chains and exit codes.

| Directory | Purpose |
|---|---|
| `src` | Types, SHA-256, chain predicates/append, verification, sampling; all SPARK On |
| `cli` | File I/O, argument parsing and orchestration; SPARK Off |
| `tests` | Ada runner and PowerShell CLI integration tests |
| `scripts` | Windows local build/test/proof/check commands |
| `docs` | Current proof report, raw log and demo transcript |
